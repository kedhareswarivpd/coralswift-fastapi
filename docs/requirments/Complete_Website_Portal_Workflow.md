# Complete Website & Portal Workflow

## 1. Public Website → Contact Form → Lead Generation

First, a user visits the public website.

The user can browse the public pages and learn about:
- Company information
- Services
- Industries
- Blogs
- Other relevant content

If the user is interested in the company or its services, they can submit the **Contact Form**.

The Contact Form should capture relevant information such as:
- Name
- Email
- Phone number
- Company
- Industry
- Required Service
- Project requirements
- Expected budget
- Other relevant requirements

The **Services** should be available as a selectable option in the Contact Form.

After the user submits the form:

**Contact Form → Lead is Generated**

---

## 2. Lead Evaluation

Once the lead is generated, the sales/admin team evaluates the lead.

The team can:
- Review the lead information
- Contact the lead
- Schedule a meeting
- Discuss the required service
- Understand project requirements
- Discuss budget
- Discuss expected delivery timeline
- Clarify other business requirements

After evaluation, the lead can have one of two outcomes:

**Successful Lead → Convert Lead to Client**

**Unsuccessful Lead → Reject/Close Lead**

---

## 3. Lead → Client Conversion

If the lead is successful, the sales/admin team converts the lead into a **Client**.

**Lead → Successful Evaluation → Convert to Client**

After conversion, the system should generate client login credentials.

The credentials can be generated by an authorized user such as:
- Admin
- Project Manager

The generated credentials should include:
- Username/Email
- Temporary Password
- Client Portal Login Information

---

## 4. Client Credential Email

Once the credentials are generated, the system should send an email to the client.

The email should contain:
- Thank-you message
- Confirmation of joining/working with the company
- Client portal login URL
- Username
- Password
- Basic login instructions

**Client Created → Credentials Generated → Email Sent → Client Logs into Client Portal**

---

## 5. Client Portal

The client uses the credentials received through email to log into the **Client Portal**.

After successful login, the client should see their own dashboard and project-related information.

The Client Dashboard should contain modules such as:
- Dashboard
- Projects
- Proposals
- Your Work / Project Progress
- Project Tracker
- Documents
- Meetings
- Invoices
- Payments
- Support / Tickets
- Notifications
- Profile

The client should only be able to access their own data.

---

## 6. Project Manager → Employee Assignment

After the client is onboarded, the **Project Manager (PM)** manages the project.

The PM can assign one or more employees to the client's project.

**Client → Project → Project Manager → Assigned Employee**

The assigned employee works on the project and updates the project progress regularly.

The PM should be responsible for coordinating:
- Client requirements
- Employee assignments
- Project progress
- Deliverables
- Client communication
- Project timelines

The client should have a controlled communication/contact mechanism through the designated PM or assigned employee rather than unrestricted internal access.

---

## 7. Proposal Workflow

If a proposal needs to be created for the client:

**Employee → PM Review → Client**

The employee prepares the proposal and submits it to the Project Manager.

The PM reviews the proposal and sends it to the client.

The client can then:

### Accept Proposal

**Proposal → Accepted → Project Duration/Timeline Confirmed → Project Starts**

### Reject Proposal

**Proposal → Rejected → Revision/New Proposal → PM Review → Client**

The system should maintain the history of proposals, including:
- Proposal version
- Created date
- Submitted date
- Status
- Client comments
- Acceptance/rejection
- Rejection reason
- Approved proposal

---

## 8. Project Tracker

Once the proposal is accepted, the project officially moves into the project execution stage.

A **Project Tracker** should be created.

The tracker should contain:
- Project name
- Client
- Assigned PM
- Assigned employees
- Start date
- Expected completion date
- Project duration
- Current status
- Overall completion percentage
- Daily updates
- Tasks
- Milestones
- Deliverables

### Daily Project Updates

Employees update the project daily.

For example:

**Day 1 → Work completed → Progress updated**

**Day 2 → Work completed → Progress updated**

**Day 3 → Work completed → Progress updated**

These updates should be visible to the PM.

The relevant project progress should also be made available to the client through the Client Portal.

---

## 9. Project Completion & Client Delivery

After the project is completed:

**Project Execution → Final Review → Project Completed**

The final project deliverables should be shared with the client.

The client can review the completed work.

If everything is approved, the client proceeds with the payment process.

---

## 10. Payment & Invoice

After the client approves the completed work:

**Client Approval → Payment → Invoice Generation**

The system should support:
- Payment tracking
- Payment status
- Payment date
- Payment amount
- Payment reference
- Invoice generation
- Invoice download
- Invoice history

After successful payment, the system should generate the corresponding invoice.

The invoice should be available inside the Client Portal.

---

## 11. Document Management

During the project lifecycle, different documents may be exchanged between the company and the client.

Examples include:
- Architecture Documents
- PRD
- TRD
- Project Documentation
- Technical Documents
- Business Documents
- Requirements Documents
- Design Documents
- Deliverables
- Other project-related files

The Client Portal should have a dedicated **Documents** page.

All documents should be stored and organized there.

The system should maintain:
- Document name
- Document type
- Uploaded by
- Upload date
- Version
- Document status
- Access permissions
- Download option

Both company users and clients should be able to upload/download documents according to their permissions.

---

## 12. Client Support / Ticket System

The Client Portal should also contain a **Support/Ticket** module.

If a client faces an issue, they can raise a support ticket.

**Client → Create Ticket → Support Team → Ticket Assigned → Resolution → Closed**

Each ticket should contain:
- Ticket ID
- Subject
- Description
- Category
- Priority
- Created date
- Assigned support employee
- Status
- Resolution
- Closed date

### Priority-Based Support

Support tickets should have priorities such as:
- Critical
- High
- Medium
- Low

For example:

**High Priority → Resolution target within 1 business day**

The system should track SLA/response and resolution deadlines based on priority.

---

## 13. Meetings

Meetings can be scheduled between:
- Client and Project Manager
- Client and Employee
- Client and other authorized team members

When a meeting is scheduled:

**Meeting Scheduled → Client Notification + Email Notification**

The client should receive:
- In-app notification
- Email notification

The meeting should contain:
- Meeting title
- Date
- Time
- Participants
- Meeting link/location
- Agenda
- Meeting status

If meetings are recorded, the recording and/or meeting notes should be stored according to the applicable access permissions.

---

## 14. Employee Portal

The system should also provide a separate **Employee Portal**.

The Employee Portal should contain:
- Employee Dashboard
- Attendance
- Leave Management
- Projects
- Tasks
- Project Updates
- Timesheets
- Performance
- Training
- Payslips
- Documents
- Notifications
- Profile

---

## 15. Attendance & Leave Management

Employees can view their attendance through the Employee Portal.

### Leave Workflow

**Employee → Apply Leave → HR → Review**

HR can:

**Approve Leave**

or

**Reject Leave**

If approved:

**Leave Request → Approved**

If rejected:

**Leave Request → Rejected**

The employee should receive the corresponding notification.

Attendance information should be accessible to authorized HR users.

---

## 16. Employee Project Management

The Project Manager assigns projects/tasks to employees.

**PM → Project → Employee Assignment**

Once assigned, the employee works on the project and submits daily progress updates.

The employee's project tracker and the client's project tracker should be connected to the same project data but display information according to each user's permissions.

### Employee View
- Detailed tasks
- Internal updates
- Work completed
- Time spent
- Technical information

### Client View
- Overall progress
- Milestones
- Deliverables
- Approved updates
- Project status

---

## 17. Employee Timesheets

Employees should have access to their timesheets.

Timesheet information can include:
- Date
- Project
- Task
- Hours worked
- Work description
- Status

Depending on the business rules, employees may have **read-only access** to finalized timesheets, while authorized users can manage/edit them.

---

## 18. Employee Performance & Training

The Employee Portal should provide:

### Performance
- Performance reviews
- Goals
- Ratings
- Feedback
- Performance history

### Training
- Assigned training
- Training materials
- Training status
- Completion records

---

## 19. Payslips

Employees should be able to view and download their payslips.

The Payslip module should contain:
- Pay period
- Salary details
- Deductions
- Net salary
- Payslip document

Employees should have access only to their own payslips.

---

## 20. Employee Documents

Employees should have a dedicated **Documents** section.

Documents may include:
- Employee documents
- HR documents
- Policies
- Certificates
- Employment documents
- Training documents
- Other authorized documents

Employees should be able to upload or download documents based on their permissions.

---

## 21. Admin Panel

The **Admin Panel** should provide centralized management of the entire system.

The Admin Panel can include:
- Dashboard
- Users
- Clients
- Employees
- Leads
- Projects
- Proposals
- Tasks
- Meetings
- Documents
- Payments
- Invoices
- Support Tickets
- HR
- CMS
- SEO
- Notifications
- Reports
- Audit Logs
- System Settings

---

## 22. Role-Based Authentication & Authorization

The system must implement **Role-Based Access Control (RBAC)**.

Possible roles include:
- Super Admin
- Admin
- Project Manager
- HR
- Employee
- Sales
- Support
- Client

Every user should only see the modules and data allowed for their role.

Examples:

**Client → Only their own client/project information**

**Employee → Assigned projects and personal HR information**

**PM → Assigned clients/projects/employees**

**HR → Employee/HR-related information**

**Admin → Full authorized system access**

---

## 23. CMS – Content Management System

The system should include a **CMS** for managing public website content.

Authorized CMS users should be able to:
- Create
- Edit
- Publish
- Unpublish
- Delete
- Manage content

CMS content can include:
- Website Pages
- Services
- Industries
- Blogs
- FAQs
- Case Studies
- Announcements
- Other public website content

Whenever CMS content is published, it should automatically become available on the corresponding public website page.

**CMS → Create Blog → Publish → Public Website Blog Page**

---

## 24. Services Management

Services should be centrally managed.

Services created in the CMS/Admin Panel should be available on:
- Public Website
- Contact Form
- Lead Management
- Proposal
- Project
- Client Portal

**Service Created → CMS → Published → Contact Form Service Selection → Lead → Proposal → Project**

---

## 25. Industries Management

The website should also support **Industries** management.

Industries can be created and managed through the CMS.

They should be displayed on the public website and can also be associated with leads, clients, and projects where required.

---

## 26. Blog Management

The CMS should allow authorized users to manage blogs.

Functions should include:
- Create Blog
- Edit Blog
- Save Draft
- Publish
- Unpublish
- Delete
- Categories
- Tags
- Featured Image
- Author
- Publication Date

Published blogs should appear automatically on the public website.

---

## 27. SEO Management

SEO is an important requirement for the public website.

Every public page should have SEO management capabilities.

SEO fields can include:
- SEO Title
- Meta Description
- Meta Keywords, if required
- URL Slug
- Canonical URL
- Open Graph Title
- Open Graph Description
- Open Graph Image
- Robots settings
- Structured data/schema where applicable

The CMS should allow authorized users to manage SEO information for newly created pages, services, industries, and blogs.

---
